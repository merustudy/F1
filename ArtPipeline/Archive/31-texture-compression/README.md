# Round 31 — 그림의 압축: Mipmap이 있는 그림이 무압축으로 들어가는 문제 (원인, 수정안, 권장안 구현, 2026-10-05)

사용자 지시: 용병 1000명의 비용·용량 검토에서 찾은 문제(밉맵을 켠 그림이 무압축)에 대해 "원인 확인, 수정안 및 권고 수정안으로 수정 수행, 체인·스크린샷 확인 순서 진행". 호출 없음.
작업 트리를 건드리는 실험은 하지 않았다. 실험은 모두 프로젝트의 APFS 복제본에서 했다(`run_probe.sh`).

## 발견

- Addressables의 빌드 기록(`Library/com.unity.addressables/buildlayout.json`, 10/3~10/4의 다섯 번 모두): 전신 그림 672x896이 3,211,208바이트 = 픽셀당 4바이트(RGBA32)와 Mipmap.
  같은 묶음의 배경(2304x1536, Mipmap 없음)은 픽셀당 1바이트(BC7). Import 정책은 모두 높은 품질의 압축(`CompressedHQ`)이다.
- 그때의 그림 묶음(`f1-art`, 자세가 들어오기 전)은 파일 10.84MB(LZ4HC), 안의 원래 크기 41.5MB.

## 원인 (실험 1: `probe/TextureProbe.cs`, 배치 모드, Unity 6000.3.9f1, StandaloneOSX)

발키리의 전신 그림을 같은 정책으로, 하나씩만 바꿔 Import했다.

| 변형 | 크기 | Mipmap | 결과 |
|---|---|---|---|
| 정책 그대로 | 672x896 | 켬 | RGBA32 |
| Mipmap 끔 | 672x896 | 끔 | **BC7** |
| 보통 품질(자동이면 DXT5) | 672x896 | 켬 | RGBA32 |
| Standalone에 BC7을 직접 지정 / DXT5를 직접 지정 | 672x896 | 켬 | RGBA32 / RGBA32 |
| Sprite 대신 Default 타입, `alphaIsTransparency` 끔 | 672x896 | 켬 | RGBA32 |
| 여백을 붙여 768x1024 (4의 배수, 2의 거듭제곱 아님) | 768x1024 | 켬 | RGBA32 |
| 여백을 붙여 1024x1024 (2의 거듭제곱) | 1024x1024 | 켬 | **BC7** |
| 768x1024, Mipmap 끔 | 768x1024 | 끔 | **BC7** |
| Crunch(높은 품질 / 보통 품질) — 실험 2 | 672x896 | 켬 | RGBA32 / RGBA32 |

- **Unity는 Mipmap이 있는 텍스처를 두 변이 모두 2의 거듭제곱일 때만 BC7·DXT로 압축한다.** 다른 크기는 어떤 압축을 요청해도 무압축(RGBA32)으로 둔다.
  Unity 문서도 같은 제한을 적는다: 크기가 2의 거듭제곱이 아니고 Mipmap이 있으면 Crunch, BC4, BC5, ASTC만 된다 [1]. 컬러 그림의 BC7·DXT1·DXT5는 안 되고, Crunch는 Import에서 무압축으로 남았다.
  Windows 빌드 모듈은 이 Mac에 없어 직접 보지 못했지만 문서의 제한은 플랫폼을 가리지 않는다.
- 해당하는 것: Mipmap을 켠 모든 그림 — 전신 11, 자세 22, 얼굴 11, 아이템 아이콘 21, 포션 2, UI 조각(`F1-UI`). 배경 하나만 압축돼 있었다.
- 무압축이면 메모리가 압축의 4배다: 전신 3.2MB(압축되면 0.8MB), 자세 10.8MB(2048x1024로 압축되면 2.8MB). 한 전투에서 그림 메모리의 대부분이 자세다(용병 넷·적 다섯의 공격·피격).
- 참고: 에디터의 품질 단계가 **Very Low**(`QualitySettings` `m_CurrentQuality: 0`, 텍스처를 절반 해상도로 제한)이고 Standalone 빌드는 **Ultra**(제한 없음)다.
  1080p에서는 둘이 같은 Mipmap 단계를 써서 차이가 없고, 그림을 원래 크기 가까이 그리는 곳(4K의 아이콘, 4K의 보스)에서만 에디터·스크린샷이 빌드보다 흐리다. 이번 수정과는 별개다.

## 실험 2: 화면에서의 차이 (`probe/TextureCompare.cs`, `compare.py`)

- 게임의 스크린샷으로는 비교하지 못했다. 전투 화면은 숨쉬기·촛불·떠오르는 글자가 실행마다 달라, 자세를 건드리지 않은 장면도 같은 코드끼리 PSNR 21~35dB로 다르다(제목·로비처럼 움직임이 없는 화면은 0).
- 대신 그림 하나를 변형마다 GPU로 게임의 크기(1080p, 보스 150%, 4K)에 그려 읽어 왔다. 필터는 게임과 같은 Bilinear(가장 가까운 Mipmap). 무대의 어두운 색 위에서, 그림이 덮는 픽셀만 잰다.

| 비교 | PSNR | 최대 차이 | 24 넘게 다른 픽셀 |
|---|---|---|---|
| 자세 1080p: 64/63배 크기 조정만 (무압축끼리) | 31.8dB | 76 | 2.47% |
| 자세 1080p: BC7 압축만 (2048x1024끼리) | 40.0dB | 40 | 0.11% |
| 자세 1080p: 권장안 전체 | 31.3dB | 73 | 2.90% |
| 자세 보스 150% / 4K: 권장안 전체 | 32.2 / 32.7dB | 99 / 88 | 2.24 / 1.98% |
| 자세 1080p: Mipmap 끔 | 20.6dB | 183 | 17.07% |
| 전신 1080p: Mipmap 끔 | 19.6dB | 187 | 19.62% |
| 아이콘 1080p(절반 크기): Mipmap 끔만 / BC7 압축만 | 59.8 / 48.0dB | 1 / 7 | 0 / 0% |

- 권장안의 차이는 대부분 64/63배 크기 조정으로 선이 1픽셀 안쪽에서 옮겨진 것이다. 압축만의 차이는 40dB 이상이다. `compare-sheet.png`(2배 확대)에서 지금과 권장안은 구별되지 않는다.
- Mipmap을 끈 그림은 훨씬 또렷하다. 지금 게임은 1080p에서 전신·자세를 1/4 해상도의 Mipmap으로 그려 키우므로 흐리다(Handoff에 적힌 것). 또렷하게 할지는 그림의 판정이다(남은 것).

## 구현 (권장안 A)

- `tools/fit_pose.py`: 맞추기와 리뷰는 지금처럼 2016x1008에서 하고, 파일로 쓸 때만 `texture()`가 2048x1024(`TEXTURE`)로 늘린다.
- `tools/review_pose.py`: 자세 파일을 2016x1008로 되돌려 대기 그림 옆에 세운다(바닥선·머리 비교는 그대로).
- 자세 22장을 다시 맞춰 `Assets/@Art/Pose/Job|Enemy`에 넣었다(호출 없음). 확인: 바꾸기 전의 도구로 다시 맞춘 2016x1008이 게임의 파일과 22장 모두 픽셀까지 같았고,
  새 2048x1024는 게임의 파일을 64/63배(LANCZOS) 한 것과 22장 모두 픽셀까지 같다. 크기 말고 바뀐 것이 없다.
- `ArtSetup`: `ImportPolicy.Compressed` — 자세·배경은 압축돼야 하고 전신·UI(아이콘·얼굴·포션)는 무압축임을 적는다. 압축돼야 하는 그림이 무압축으로 Import되면 `FindProblems`가 잡는다(2016x1008 자세를 다시 넣으면 체인이 실패한다).
- 문서: Architecture/13 "후처리 (`pose`)"·"Unity 배선"·"Import 정책", Architecture/12 "유닛의 그림". 게임 코드와 데이터는 그대로다.

## 남은 것 (판정)

- 전신·UI·아이콘·얼굴·포션은 무압축으로 남는다(D·B). 전신 11장이 약 35MB(메모리). 용병 그림을 크게 늘리면 D를 그 설계와 함께 한다.
- 또렷함: Mipmap 끔(B) 또는 다른 방법(Trilinear, Mip bias)으로 전신·자세를 또렷하게 할지. 목업(MP4, 숨쉬기와 돌진)으로 본다.
- 에디터의 품질 단계 Very Low: 빌드(Ultra)와 맞출지.
