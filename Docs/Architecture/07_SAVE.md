# 07. Save

Save 파일의 형식과 I/O, Backup과 복구, Migration, 저장 시점을 소유한다.

## 파일

경로는 `<persistentDataPath>/Saves/`다. 파일마다 같은 Directory에 `.tmp`와 한 세대 `.bak`이 있다.

`persistentDataPath`는 Windows에서는 `companyName`과 `productName`으로, macOS Player에서는 Bundle Identifier로 정해진다
(Editor에서는 macOS도 `companyName/productName`이다). 셋 중 하나를 바꾸면 기존 Save를 찾지 못한다. 값은 `ProjectSetup`이 가진다.

| 파일 | 내용 | 주인 |
|---|---|---|
| `settings.json` | 전역 설정 (Locale, 음악·효과음의 음량) | `SettingManager` |
| `run.json` | 진행 중인 런 하나: 런 상태, 원정 진행 상태, 진행 중인 전투의 재현 기록 | `RunManager` |

저장 슬롯은 하나다. 새 런은 기존 `run.json`을 덮어쓴다.

## 책임

- `SaveManager`는 형식과 I/O만 한다: 직렬화, Atomic Write, Backup, 손상 복구.
- 상태를 적용하는 것은 그 상태의 주인이다. `SaveManager`는 Gameplay를 모른다.
- Save DTO는 Runtime State나 Domain Type이 아니다. DTO는 `Assets/@Scripts/Save/Models`에 두고 주인이 변환한다.
- DTO는 `SchemaVersion`을 가진다. 버전이 오르면 주인이 단계별 Migration 함수를 둔다.

## Atomic Write와 Backup

```text
같은 Directory에 .tmp 쓰기 -> Flush -> 기존 파일이 있으면 Replace(기존 파일은 .bak이 된다), 없으면 Move
```

- `.tmp`는 Load 후보가 아니다. 저장소를 초기화할 때 남아 있는 `.tmp`를 지운다.
- Load는 Primary를 읽고 검증한다. 실패하면 `.bak`을 읽고 검증한다.
- `.bak`으로 복구했으면 Primary를 `.bak` 내용으로 다시 쓴다. 이때 `.bak`은 건드리지 않는다(손상된 Primary가 정상 `.bak`을 덮지 않게).
- 둘 다 읽을 수 없으면 `Corrupt`다. 어떻게 할지는 주인이 정한다. 설정은 기본값으로 되돌린다.

## 저장 시점과 순서

```text
명령 검증 -> 상태 변경 -> Stable State -> 직렬화 Snapshot -> Atomic Save 성공 -> Typed Event -> UI/연출
```

- 상태가 확정될 때마다 저장한다. Build, Quit, Pause 시점의 마지막 저장에 의존하지 않는다.
- 확정된 손실(용병의 사망)은 이어하기로 되돌릴 수 없어야 한다.
- 저장에 실패하면 그 변경은 확정되지 않은 것이다. 주인은 상태를 되돌리거나(설정), 같은 Snapshot의 저장이 성공할 때까지
  다음 변경을 막는다(런). 실패를 무시하고 진행하지 않는다.
- Test는 전용 Save Root를 쓴다. 실제 Save 폴더를 건드리지 않는다.

## run.json

`RunManager`가 유일한 주인이다. 파일 하나에 런과 원정을 함께 담아서, 귀환 정산처럼 둘이 같이 바뀌는 변경이 한 번의 Atomic Write로 확정된다.
`ExpeditionManager`는 파일을 쓰지 않는다. 자기 부분(원정과 전투 기록)을 DTO로 만들어 `RunManager`에 넘긴다.

```text
RunSaveData
├─ SchemaVersion
├─ Run          시드, 날짜, 로스터(id, 직업, 피로도), 전사자, 파티, 원정 횟수, 클리어 기록, 종료 여부
└─ Expedition   (원정 중일 때만) 던전, 시드, 구성원(HP, 열, 보드, 피로도), 인벤토리, 포션, 단계, 현재 노드, 전리품(주운 자리는 null), 지역 코인, (상점에 있을 때만) 상점의 물건과 새로고침 횟수
   └─ Battle    (전투 중일 때만) 받아들여진 입력 목록, 확정 시각, 그 시각까지의 로그 요약값
```

- DTO는 `Assets/@Scripts/Save/Models/RunSaveData.cs`다. 문자열, 정수, bool, 목록만 가진다. Enum은 이름 문자열로, 시드는 10진 문자열로,
  열은 번호로 적는다(1열이 1). 보드는 아이템(id, 등급, 기본 무기인지)의 순서 있는 목록이고 빈 칸은 적지 않는다. 인벤토리도 같은 목록이다.
  보드의 칸 수와 아이템의 크기는 Static Data에서 온다. 피로도는 0에서 쌓이는 값이다(`Docs/Design/04_Lobby_100Day_Economy.md` §3):
  로스터의 것은 원정 사이에, 구성원의 것은 원정 동안 쓰이고 귀환 정산에서 로스터로 간다.
- DTO와 상태 사이의 변환과 검증은 주인 쪽 코드(`F1.Flow.RunSaveMapper`)가 한다. Domain Type은 직렬화 Attribute를 갖지 않는다.
- 저장하지 않는 것: 맵(원정 시드에서 다시 만든다), 전투 중의 유닛 상태와 이벤트 로그(Setup과 입력 기록에서 다시 만든다),
  정산 보고, 화면 상태(고른 칸, 배속).

### 저장 시점

상태를 바꾸는 명령 하나가 끝날 때마다 저장한다.

| 명령 | 저장되는 것 |
|---|---|
| 새 런, 파티에 넣기와 빼기와 자리 바꾸기, 쉬기 | 런 |
| 출발, 노드 들어가기 | 런 + 원정 (전투 노드에 들어가면 빈 전투 기록이 생긴다. 야영지 노드는 단계 `AtCamp`만. 상점 노드는 단계 `AtShop`과 뽑힌 물건) |
| 야영지에서 쉬기와 정비 | 원정 |
| 상점에서 사기(보드, 인벤토리, 포션), 새로고침, 나가기 | 원정 (코인, 판 자리, 새로고침 횟수; 나가면 상점 기록이 없어진다) |
| 포션 사용, 후퇴 시도(성공과 실패 모두) | 입력 목록과 확정 시각 |
| 전투 진행 중 아군이 빈사가 되거나 죽었을 때 | 확정 시각 |
| 전투 종료 | 원정에 반영된 결과. 원정이 끝났으면 귀환 정산까지 반영된 런(원정 없음) |
| 전리품 줍기(보드나 인벤토리로. 하나마다)와 두고 가기, 아이템 옮기기(보드 사이, 보드와 인벤토리 사이), 자리 바꾸기 | 원정 |

- 전투 화면을 닫는 것과 정산 보고를 확인하는 것은 상태를 바꾸지 않으므로 저장하지 않는다.
- 전투 시간이 흐르는 것만으로는 저장하지 않는다.

### 이어하기

- Boot가 `run.json`을 읽어 런과 원정을 되살린다(BOOT-09). 타이틀의 "이어하기"는 되살아난 단계의 화면으로 간다.
- 전투 중이었다면 `BattleEngine.Replay(Setup, 입력 목록, 확정 시각)`으로 그 시각의 전투를 다시 만든다.
  Setup은 저장된 원정 상태에서 다시 만들어지고(`ExpeditionRules.BuildBattleSetup`), 결과는 Setup과 입력만의 함수라서 같은 전투가 나온다.
- **확정된 손실은 되돌릴 수 없다.** 아군이 죽은 순간과 빈사가 된 순간, 그리고 모든 입력이 확정 시각과 함께 저장돼 있다.
  이어하면 적어도 그 시각까지는 같은 입력으로 재현되므로 죽음은 다시 일어난다. 후퇴 판정도 시도 순서대로 같은 굴림이 나온다.
- 확정 시각 뒤에 흐른 전투 시간은 저장되지 않는다. 그 구간은 이어했을 때 다시 진행한다. 그 구간에 죽음이나 입력이 있었다면 저장됐을 것이므로,
  되감기는 것은 아무 일도 확정되지 않은 시간뿐이다.
- 재현한 로그의 요약값이 저장된 값과 다르면(게임 규칙이나 데이터가 바뀐 경우) 지금 규칙으로 재현한 상태를 쓴다.
  입력 기록이 지금 규칙에서 성립하지 않으면 그 전투를 처음부터 다시 한다. 어느 쪽이었는지는 `ExpeditionManager.LastResume`이 말해 준다.
- **전리품을 줍다 끝냈다면**(`PickingLoot`. 2026-10-08 Round 47: 전리품은 전투 화면에서 줍는다) 전투 기록은 이미 없다(이긴 순간 `CompleteBattle`이 전리품과 함께 저장했다). 이어하기는 전투 화면을
  **"이긴 뒤" 모습**으로 연다: 파티는 저장된 그대로 서 있고(엔진은 그 파티로 새로 세우며 돌지 않는다) 적은 없으며, 전리품은 저장된 그대로 바닥에 놓인다. 전사자·코인·로그는 저장하지 않는 것이라 없다(띠는 "전리품"만 말한다). 저장 형식은 그대로다(`12_UI.md` "전투 화면"의 "이긴 뒤").
- 정산 보고를 확인하기 전에 끝냈다면 다음에는 로비에서 시작한다(정산은 이미 저장돼 있다).
- 파일을 사람이 직접 고치거나 지우는 것까지 막지는 않는다.

### 읽기와 검증

`SaveManager.Load`의 검증 함수가 DTO를 실제 상태로 바꿔 본다. 하나라도 어긋나면 그 파일은 무효다.

- `SchemaVersion`이 읽을 수 있는 범위 밖, 모르는 id(용병, 직업, 던전, 아이템, 포션), 모르는 Enum 이름
- 범위를 벗어난 수(날짜, 로스터와 구성원의 피로도(0~`MaxFatigue`), HP, 등급, 열), 모르는 단계 이름, 모르는 피로 상태·로스터의 각성·100 아래의 고통, 파티 규칙 위반, 보드가 직업의 칸 수를 넘음, 인벤토리가 `InventoryCells`를 넘음, 보드나 인벤토리 목록의 누락
- 기본 무기로 적힌 아이템이 어느 직업의 무기도 아님(찾은 아이템이 피로가 들지 않는 것으로 바뀌지 않게)
- 자리 규칙 위반: 한 열에 둘이 섬, 살아 있는 용병 앞에 빈 열이 있음 (로비 파티와 원정 구성원 모두)
- 단계와 맞지 않는 기록(전투 중이 아닌데 전투 기록이 있음, 전리품 단계가 아닌데 전리품이 있음, 야영지 단계(`AtCamp`)인데 현재 노드가 야영지가 아님,
  야영지 노드에서 전리품을 줍거나 원정이 끝남; 상점 단계(`AtShop`)와 상점 기록이 서로 어긋남, 상점 노드가 아닌데 상점 단계임, 물건이 `ShopSlots`보다 많음, 모르는 물건, 음수의 새로고침 횟수나 코인)

Primary가 무효면 `.bak`을 같은 방식으로 검증해 쓴다. 둘 다 무효면 런이 없는 것으로 시작하고, 타이틀이 그 사실을 알린다.
새 런은 그대로 시작할 수 있다.

### 저장 실패

- 저장에 실패하면 `RunManager`는 **막힌 상태**가 된다(`IsSaveBlocked`). 실패한 Snapshot의 byte를 그대로 쥐고 있다.
- 막힌 동안 상태를 바꾸는 명령은 모두 예외다. 전투 시간도 흐르지 않는다.
- `RetrySave`는 쥐고 있던 **같은 byte**만 다시 쓴다. 성공하면 풀린다.
- 화면은 막힘을 알리는 Overlay를 띄워 다른 조작을 막고, 다시 시도와 종료만 받는다.
- 막힌 채로 끝내면 마지막 변경은 확정되지 않은 것이다. 다음에는 마지막으로 저장에 성공한 상태에서 시작한다.

### Schema Version

- `RunSaveData.SchemaVersion`은 구조가 바뀔 때 올린다. `RunSaveMigrator`가 옛 버전을 한 단계씩 올린 뒤 검증한다.
- 지금 버전보다 새로운 파일은 읽지 않는다(무효).
- 지금 버전은 9다(2026-10-07, 18단계: 전리품 `Loot` — 마지막 전투의 드랍 목록, 주운 자리는 null — 이 보상 후보 `PendingRewards`를 대신한다). 8은 `From8To9`가 올린다:
  보상을 고르던 단계(`ChoosingReward`)는 노드 고르기(`ChoosingNode`)가 되고 전리품은 비어 있다(그 보상 하나는 잃는다. 8의 `PendingRewards`는 읽지 않는다: 모르는 필드는 무시한다).
  검증: 전리품은 줍는 단계(`PickingLoot`)에만 있고, 셋(`BalanceData.MaxLootCards`)을 넘지 않으며, 모두 아는 아이템이고(포션은 떨어지지 않는다), 적어도 하나는 아직 놓여 있다(마지막 것을 주우면 단계가 끝난다).
- 8(2026-10-07, 17단계: 원정의 지역 코인 `Coins`와, 상점에 있을 때의 `Shop`(물건의 목록 — 판 자리는 null — 과 새로고침 횟수)). 7은 `From7To8`가 올린다:
  코인은 0(DTO의 기본값), 상점은 없음(null). 7의 어느 단계도 상점의 것이 아니다.
- 7(2026-10-07, Round 41: 아이템과 보상의 단계 이름이 일반·동·은·금(`Common`·`Bronze`·`Silver`·`Gold`)이다). 6은 `From6To7`가 올린다:
  6의 Bronze·Silver·Gold·Diamond를 Common·Bronze·Silver·Gold로 이름만 바꾼다(같은 넷, 한 칸씩). 모르는 이름은 그대로 두어 검증이 거른다.
- 6(2026-10-06, Slice B 15단계: 로스터의 용병이 고통(`Affliction`)을, 원정의 구성원이 고통이나 각성(`State`)을 `FatigueState`의 id로 적는다. 없으면 null).
  5는 `From5To6`가 올린다: 아무도 상태가 없다(null 그대로). 검증: 모르는 id는 무효, 로스터에 각성은 무효, 고통은 피로가 `FatigueBreakdown` 이상이어야 한다(아래면 풀렸을 것이다).
- 5(2026-10-06, 14단계: 아이템과 보상이 단계(`Tier`, 이름으로)를 적는다). 4는 `From4To5`가 올린다: 모든 아이템과 보상이 5의 이름으로 동(지금의 일반)이다.
  단계를 적지 않은 항목은 일반으로 읽는다(DTO의 기본값). 모르는 이름이나 비운 이름(null)은 무효이고, 포션 보상은 일반이어야 한다.
- 4(2026-10-06, 12단계: 피로도가 0에서 쌓이는 값이고, 구성원이 피로도를 갖고, 아이템이 기본 무기인지 적는다).
  13단계의 원정 단계 `AtCamp`(야영지)는 단계 이름이 하나 는 것이라 DTO의 모양이 그대로이고 버전을 올리지 않았다.
  3(보드는 빈 칸 없는 아이템 목록, 원정에 인벤토리)은 `From3To4`가 올린다: 로스터의 피로도는 남은 양(최대 100에서 뺀 값)이었으므로 100에서 빼서
  쌓인 양으로 바꾸고(이 100은 버전 3 파일의 뜻이지 지금의 규칙이 아니다), 원정의 구성원은 그 용병이 떠날 때의 피로도를 갖고,
  어느 직업의 무기인 아이템은 기본 무기로 적는다(직업의 무기는 보상으로 나온 적이 없다). 변환은 Static Data를 받는다.
  2(열을 번호로 적고, 보드는 칸마다 아이템이나 null)는 `From2To3`가 3으로 올린다: null을 빼고 빈 인벤토리를 더한다. 그 뒤의 검증에서 보드가 직업의 칸 수를 넘으면(아이템의 크기가 데이터로 생겼으므로)
  그 파일은 무효다. 인벤토리의 용량(`InventoryCells`)도 같다: DTO의 모양은 그대로라 버전을 올리지 않았고, 넘치는 파일은 검증이 거른다.
  1(전열/후열 두 열)은 **읽지 않는다**(`OldestReadableVersion`). 변환하지 않는다:
  전투 규칙이 달라 저장된 전투 기록이 재현되지 않는다. 타이틀은 읽을 수 없는 파일이 있다고 알리고 새 런을 받는다.
- 열의 수, 적 무리의 구성, 쓸 수 있는 자리의 셈법처럼 **DTO의 모양을 바꾸지 않는 규칙 변경**에는 버전을 올리지 않는다. 그런 파일은 읽히고,
  진행 중이던 전투는 지금 규칙으로 재현된다("이어하기"의 `Diverged`, `Restarted`).
- 옛 버전을 읽지 않기로 하는 것은 사용자가 정한다. 그런 결정이 없으면 버전을 올릴 때 변환 단계를 같이 넣는다.
- Static Data의 내용이 바뀌어 id가 없어진 것은 버전으로 다루지 않는다. 검증에서 무효가 된다.
- `SettingsData.SchemaVersion`은 2다(2026-10-05, 10단계): 음악·효과음의 음량 `MusicVolume`, `EffectVolume`(0~100의 정수)을 더했다.
  1은 둘을 100으로 채워 올린다(그대로 읽으면 0이라 소리가 꺼진다). 범위 밖의 음량은 가까운 끝(0이나 100)으로 고쳐 저장한다(알 수 없는 언어를 기본값으로 고치는 것과 같다).

## Validation

- 새 Save 파일이 위 표에 있고 주인이 하나인가?
- 상태를 바꾸는 새 명령이 끝에서 저장하는가? 막힌 상태에서 거부되는가?
- DTO에 새 Field를 넣었다면 변환, 검증, 왕복(Round-trip) Test를 같이 고쳤는가?
- 저장 실패 경로에 Test가 있는가?
- DTO를 Domain이나 Runtime State로 쓰지 않는가?
- Test가 실제 Save 폴더를 쓰지 않는가?

## Deferred and Forbidden

- Deferred: 여러 저장 슬롯, 클라우드 저장, 암호화와 변조 방지, 전투 시간의 주기적 저장.
- Forbidden: `.tmp`를 Load 후보로 쓰기, 종료 시점 저장에 의존, 저장 실패를 Warning으로 넘기기, `PlayerPrefs`에 진행 상태 저장.
