# 07. Save

Save 파일의 형식과 I/O, Backup과 복구, Migration, 저장 시점을 소유한다.

## 파일

경로는 `<persistentDataPath>/Saves/`다. 파일마다 같은 Directory에 `.tmp`와 한 세대 `.bak`이 있다.

| 파일 | 내용 | 주인 |
|---|---|---|
| `settings.json` | 전역 설정 (Locale) | `SettingManager` |
| `run.json` | 진행 중인 런 하나: 런 상태, 원정 진행 상태, 진행 중인 전투의 재현 기록 | `RunManager` |

저장 슬롯은 하나다. 새 런은 기존 `run.json`을 덮어쓴다.

## 책임

- `SaveManager`는 형식과 I/O만 한다: 직렬화, Atomic Write, Backup, 손상 복구.
- 상태를 적용하는 것은 그 상태의 주인이다. `SaveManager`는 Gameplay를 모른다.
- Save DTO는 Runtime State나 Domain Type이 아니다. DTO는 `Assets/@Scripts/Save/Models`에 두고 주인이 변환한다.
- DTO는 `SchemaVersion`을 가진다. 버전이 오르면 주인이 단계별 Migration 함수를 둔다.

## Atomic Write와 Backup

```text
같은 Directory에 .tmp 쓰기 -> Flush -> 기존 파일이 있으면 Replace(기존 파일은 .bak이 된다), 없으면 Move
```

- `.tmp`는 Load 후보가 아니다. 저장소를 초기화할 때 남아 있는 `.tmp`를 지운다.
- Load는 Primary를 읽고 검증한다. 실패하면 `.bak`을 읽고 검증한다.
- `.bak`으로 복구했으면 Primary를 `.bak` 내용으로 다시 쓴다. 이때 `.bak`은 건드리지 않는다(손상된 Primary가 정상 `.bak`을 덮지 않게).
- 둘 다 읽을 수 없으면 `Corrupt`다. 어떻게 할지는 주인이 정한다. 설정은 기본값으로 되돌린다.

## 저장 시점과 순서

```text
명령 검증 -> 상태 변경 -> Stable State -> 직렬화 Snapshot -> Atomic Save 성공 -> Typed Event -> UI/연출
```

- 상태가 확정될 때마다 저장한다. Build, Quit, Pause 시점의 마지막 저장에 의존하지 않는다.
- 확정된 손실(용병의 사망)은 이어하기로 되돌릴 수 없어야 한다.
- 저장에 실패하면 그 변경은 확정되지 않은 것이다. 주인은 상태를 되돌리거나(설정), 같은 Snapshot의 저장이 성공할 때까지
  다음 변경을 막는다(런). 실패를 무시하고 진행하지 않는다.
- Test는 전용 Save Root를 쓴다. 실제 Save 폴더를 건드리지 않는다.

## run.json

`RunManager`가 유일한 주인이다. 파일 하나에 런과 원정을 함께 담아서, 귀환 정산처럼 둘이 같이 바뀌는 변경이 한 번의 Atomic Write로 확정된다.
`ExpeditionManager`는 파일을 쓰지 않는다. 자기 부분(원정과 전투 기록)을 DTO로 만들어 `RunManager`에 넘긴다.

```text
RunSaveData
├─ SchemaVersion
├─ Run          시드, 날짜, 로스터(id, 직업, 피로도), 전사자, 파티, 원정 횟수, 클리어 기록, 종료 여부
└─ Expedition   (원정 중일 때만) 던전, 시드, 구성원(HP, 열, 아이템 칸), 포션, 단계, 현재 노드, 보상 후보
   └─ Battle    (전투 중일 때만) 받아들여진 입력 목록, 확정 시각, 그 시각까지의 로그 요약값
```

- DTO는 `Assets/@Scripts/Save/Models/RunSaveData.cs`다. 문자열, 정수, bool, 목록만 가진다. Enum은 이름 문자열로, 시드는 10진 문자열로 적는다.
- DTO와 상태 사이의 변환과 검증은 주인 쪽 코드(`F1.Flow.RunSaveMapper`)가 한다. Domain Type은 직렬화 Attribute를 갖지 않는다.
- 저장하지 않는 것: 맵(원정 시드에서 다시 만든다), 전투 중의 유닛 상태와 이벤트 로그(Setup과 입력 기록에서 다시 만든다),
  정산 보고, 화면 상태(고른 칸, 배속).

### 저장 시점

상태를 바꾸는 명령 하나가 끝날 때마다 저장한다.

| 명령 | 저장되는 것 |
|---|---|
| 새 런, 파티 정하기, 쉬기 | 런 |
| 출발, 노드 들어가기 | 런 + 원정 (노드에 들어가면 빈 전투 기록이 생긴다) |
| 포션 사용, 후퇴 시도(성공과 실패 모두) | 입력 목록과 확정 시각 |
| 전투 진행 중 아군이 빈사가 되거나 죽었을 때 | 확정 시각 |
| 전투 종료 | 원정에 반영된 결과. 원정이 끝났으면 귀환 정산까지 반영된 런(원정 없음) |
| 보상 받기와 넘기기, 아이템 옮기기, 열 바꾸기 | 원정 |

- 전투 화면을 닫는 것과 정산 보고를 확인하는 것은 상태를 바꾸지 않으므로 저장하지 않는다.
- 전투 시간이 흐르는 것만으로는 저장하지 않는다.

### 이어하기

- Boot가 `run.json`을 읽어 런과 원정을 되살린다(BOOT-09). 타이틀의 "이어하기"는 되살아난 단계의 화면으로 간다.
- 전투 중이었다면 `BattleEngine.Replay(Setup, 입력 목록, 확정 시각)`으로 그 시각의 전투를 다시 만든다.
  Setup은 저장된 원정 상태에서 다시 만들어지고(`ExpeditionRules.BuildBattleSetup`), 결과는 Setup과 입력만의 함수라서 같은 전투가 나온다.
- **확정된 손실은 되돌릴 수 없다.** 아군이 죽은 순간과 빈사가 된 순간, 그리고 모든 입력이 확정 시각과 함께 저장돼 있다.
  이어하면 적어도 그 시각까지는 같은 입력으로 재현되므로 죽음은 다시 일어난다. 후퇴 판정도 시도 순서대로 같은 굴림이 나온다.
- 확정 시각 뒤에 흐른 전투 시간은 저장되지 않는다. 그 구간은 이어했을 때 다시 진행한다. 그 구간에 죽음이나 입력이 있었다면 저장됐을 것이므로,
  되감기는 것은 아무 일도 확정되지 않은 시간뿐이다.
- 재현한 로그의 요약값이 저장된 값과 다르면(게임 규칙이나 데이터가 바뀐 경우) 지금 규칙으로 재현한 상태를 쓴다.
  입력 기록이 지금 규칙에서 성립하지 않으면 그 전투를 처음부터 다시 한다. 어느 쪽이었는지는 `ExpeditionManager.LastResume`이 말해 준다.
- 정산 보고를 확인하기 전에 끝냈다면 다음에는 로비에서 시작한다(정산은 이미 저장돼 있다).
- 파일을 사람이 직접 고치거나 지우는 것까지 막지는 않는다.

### 읽기와 검증

`SaveManager.Load`의 검증 함수가 DTO를 실제 상태로 바꿔 본다. 하나라도 어긋나면 그 파일은 무효다.

- `SchemaVersion`이 읽을 수 있는 범위 밖, 모르는 id(용병, 직업, 던전, 아이템, 포션), 모르는 Enum 이름
- 범위를 벗어난 수(날짜, 피로도, HP, 등급), 파티 규칙 위반, 칸 수 불일치
- 단계와 맞지 않는 기록(전투 중이 아닌데 전투 기록이 있음, 보상 단계가 아닌데 보상 후보가 있음)

Primary가 무효면 `.bak`을 같은 방식으로 검증해 쓴다. 둘 다 무효면 런이 없는 것으로 시작하고, 타이틀이 그 사실을 알린다.
새 런은 그대로 시작할 수 있다.

### 저장 실패

- 저장에 실패하면 `RunManager`는 **막힌 상태**가 된다(`IsSaveBlocked`). 실패한 Snapshot의 byte를 그대로 쥐고 있다.
- 막힌 동안 상태를 바꾸는 명령은 모두 예외다. 전투 시간도 흐르지 않는다.
- `RetrySave`는 쥐고 있던 **같은 byte**만 다시 쓴다. 성공하면 풀린다.
- 화면은 막힘을 알리는 Overlay를 띄워 다른 조작을 막고, 다시 시도와 종료만 받는다.
- 막힌 채로 끝내면 마지막 변경은 확정되지 않은 것이다. 다음에는 마지막으로 저장에 성공한 상태에서 시작한다.

### Schema Version

- `RunSaveData.SchemaVersion`은 구조가 바뀔 때 올린다. `RunSaveMigrator`가 옛 버전을 한 단계씩 올린 뒤 검증한다.
- 지금 버전보다 새로운 파일은 읽지 않는다(무효).
- Static Data의 내용이 바뀌어 id가 없어진 것은 버전으로 다루지 않는다. 검증에서 무효가 된다.

## Validation

- 새 Save 파일이 위 표에 있고 주인이 하나인가?
- 상태를 바꾸는 새 명령이 끝에서 저장하는가? 막힌 상태에서 거부되는가?
- DTO에 새 Field를 넣었다면 변환, 검증, 왕복(Round-trip) Test를 같이 고쳤는가?
- 저장 실패 경로에 Test가 있는가?
- DTO를 Domain이나 Runtime State로 쓰지 않는가?
- Test가 실제 Save 폴더를 쓰지 않는가?

## Deferred and Forbidden

- Deferred: 여러 저장 슬롯, 클라우드 저장, 암호화와 변조 방지, 전투 시간의 주기적 저장.
- Forbidden: `.tmp`를 Load 후보로 쓰기, 종료 시점 저장에 의존, 저장 실패를 Warning으로 넘기기, `PlayerPrefs`에 진행 상태 저장.
