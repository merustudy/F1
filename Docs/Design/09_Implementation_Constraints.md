## 2. 기준 구현 — 【확정】 (2026-09-30)
- 【확정】 **C# Domain이 전투 기준 구현**이다. `sim.py`는 없다. Python 시뮬을 다시 만들지 않고, 시뮬은 같은 Domain 코드를 Unity 밖에서(헤드리스) 돌리는 실행기로 새로 만든다.
- 【확정】 모든 밸런스 결정은 시뮬로 검증한 뒤 문서화한다 (08).
- 이전 기록의 후보 (a) sim.py 오라클, (c) 역할 분리는 채택하지 않았다.
- 전투 코어의 구조는 규칙 재정의가 승인된 뒤에 Docs/Architecture 에서 정한다.

## 3. 데이터 원천 형식 — 【확정】 (2026-09-30)
- 【확정】 원천은 **CSV**다. CSV에서 JSON을 생성하고, 시뮬(§2)과 게임은 **같은 생성 JSON**을 읽는다.
- 불변조건은 "**단일 원천 + 코드 하드코딩 금지 + 시뮬과 게임이 같은 원천**"이다. 파이프라인의 구조는 아키텍처가 정한다.
- 원천이 둘로 갈리면 시뮬 우선 워크플로가 깨진다.

## 4. 시뮬 우선 워크플로 【확정】
데이터 패치 → 시뮬 실행(변경 전후 같은 시드) → 수치 보고(승률, 사망 수, 사망 원인, 절벽 여부) → 확정된 것만 문서 갱신

## 5. 결정론 세부 — 【확정】 (2026-09-30 일괄 승인)
- 시간은 **정수 밀리초**다. 전투는 다음 사건의 시각으로 건너뛰며 진행한다. 같은 시각의 처리 순서는 고정이다 (→ 02_Combat_System §3).
- 난수는 시드에서 나온 난수기(PCG32)만 쓴다. 용도별로 스트림을 나눈다: 맵, 보상, 전투(사망 판정), 입력(후퇴 판정).
  런 시드에서 원정 시드를, 원정 시드에서 전투 시드를 정해진 방식으로 파생한다.
- 수치는 정수만 쓴다. 비율은 백분율이나 천분율 정수이고, 반올림 규칙을 규칙마다 적는다.
- 표현 계층은 전투 코어의 이벤트 로그를 재생한다 → 연출이 결과를 바꾸지 못한다
- 같은 시드로 N회 실행 결과 동일 테스트를 검증 체인에 포함 (기준 구현이 C# 하나이므로 구현 간 패리티 테스트는 없다)
